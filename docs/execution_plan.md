# Pick 5 Pool — Execution Plan for `plan_3.0.md`

Sequencing for building the full launch scope described in `plan_3.0.md` (which now fully incorporates the former `plan_4.0.md` roadmap — that document is retired). Each phase has a checkpoint you can actually verify before moving on — nothing here assumes the previous phase was perfect, just that it's demonstrably working. This is a planning document only; no phase has been started yet.

## Phase 1 — Server skeleton + profile routes

Build: `firebaseAdmin.js`, `app.js`, `index.js`, `middleware/auth.js`, `routes/profile.js` (`GET /api/profile/me`, `PATCH /api/profile`).

**Goal**: `npm start` serves the exact same frontend you have today (via `express.static`, unchanged HTML/CSS/JS, no Firestore schema changes yet). Rather than a throwaway test route, `routes/profile.js` doubles as the real first proof that `verifyIdToken` works — it's the simplest possible authenticated, persisted endpoint (global, not league-scoped), and Phase 4's signup flow depends on it existing.

**Checkpoint**: site loads identically to today at `localhost:3000`; `GET /api/profile/me` without a token → 401; with a valid token → 200; `PATCH /api/profile` with a new displayName updates both the Firebase Auth record and the `users/{uid}` Firestore doc.

## Phase 2 — Global data (games, poller, config) — still no leagues

Build: `espn/mapGames.js`, `espn/poller.js`, `routes/games.js`, `routes/lastUpdated.js`, `routes/config.js`.

**Goal**: prove the ESPN JSON-API poller and adaptive interval work before any league complexity is layered on. `/api/games` output shape should match today's `games.json` exactly, so the *existing* `dashboard.js`/`picks.js` can point at it with just a URL change, as a standalone sanity check.

**Checkpoint**: `/api/games` returns real current-week data; `/api/config/season` returns `{year, lockAt, locked: false}`; manually forcing a game to `In Progress` (or testing against a live game window) drops the poll interval to 60s, confirmed via server logs.

## Phase 3 — League data model + routes

Build: `middleware/seasonLock.js`, `store.js` (league-keyed), `scoring.js` (per-league), `routes/leagues.js` (including `PATCH /api/leagues/:id/members/me` for self-service per-league display name/photo — see `plan_3.0.md`'s Data Model for the `members/{uid}` shape and the pre-fill-at-join-time behavior), `routes/leaguePicks.js`.

**Goal**: the core new domain. No frontend changes yet — verify entirely via `curl`/Postman using two real test accounts' ID tokens.

**Checkpoint**:
- Create a league with account A → appears in `GET /api/leagues/mine` for A; confirm A's `members/{uid}` doc was auto-created and pre-filled from A's global profile (`displayName`/`photoURL`, plus the debug-only `globalDisplayName`/`email`).
- Join it with account B via the invite code → appears for B too, same pre-fill check.
- `PATCH /api/leagues/:id` (owner-only) updates name/photo; confirm B (non-owner) gets rejected.
- `PATCH /api/leagues/:id/members/me` — B edits their own per-league display name/photo; confirm it only changes B's copy in this league (join a second league as B, confirm that one still shows B's global default, unaffected).
- Both submit picks for a couple weeks via `PUT /api/leagues/:id/picks/:week`.
- `GET /api/leagues/:id/scores` shows correct standings for both.
- `POST /api/leagues/:id/picks/import` copies A's picks from a second league into this one (create a throwaway second league for this check).
- `GET /api/leagues/:id/stats` returns sensible in-season numbers (this and `seasons/:year` below don't depend on `winProbability.js`, so they're fully testable here — only `my-week`'s win-% figure waits for Phase 5).
- Real `seasons/2025` + "The Sunroom" league's migrated 2025 picks already exist in Firestore (migrated 2026-08-08, see project handoff notes) — confirm `GET /api/leagues/:id/seasons/2025` computes correct historical standings against that real data, no rollover step, and correctly falls back to global `users/{uid}.displayName` for migrated players who aren't currently members of that league.
- Temporarily set `config/season.lockAt` to the past → creating/joining/submitting all get rejected server-side; set it back to the real date afterward.

## Phase 3b — League management, message board

`leave`, kick (`DELETE .../members/:uid`), `transfer-owner`, and archive (`DELETE /api/leagues/:id`) ended up built as part of Phase 3's `routes/leagues.js` (they followed the same patterns as everything else built there) and were fully checkpoint-verified on 2026-08-09 — see below. What's actually left for this phase: the `posts` CRUD routes, and extending `store.js` to cache each league's recent posts in memory (same write-through pattern as picks — Firestore write, then update the in-memory list).

**Goal**: everything from the roadmap's league-owner brainstorm that has an actual spec now (name/photo already covered in Phase 3) — verified via `curl`/Postman, same as Phase 3. The announcement-email route is deferred — see `backlog.md`.

**Checkpoint**:
- ✅ A member calls `POST /api/leagues/:id/leave` → no longer appears in the roster, can no longer read/write picks for that league. Also verified: an owner is rejected from leaving (must transfer ownership first).
- ✅ Owner kicks a different member → they no longer appear in the roster, but their already-submitted picks for the season are untouched. Also verified: owner can't kick themselves, non-owner can't kick anyone.
- ✅ Owner transfers ownership to another member → `PATCH`/owner-only actions now require the new owner's token, not the old one's. Also verified: target must already be a member, non-owner can't initiate a transfer.
- ✅ Owner archives the league → it drops out of `GET /api/leagues/mine` for all members, but the Firestore doc still exists with `archived: true` (soft-delete, not erased — no route currently fetches a single league by ID directly, so this was confirmed via direct Firestore read rather than an API call).
- ✅ A member posts to the message board, another member reads it, the owner deletes it; a non-owner/non-author delete attempt is rejected. Also verified: newest-first ordering, empty-body rejection, and the edge case of deleting a post older than the in-memory "recent" cache window (falls back to a direct Firestore lookup, both for the author-can-delete case and correctly rejecting a non-owner/non-author there too).

**Phase 3b complete as of 2026-08-09.**

## Phase 4 — Frontend rewiring (existing pages)

Build: `src/js/util/api.js`; update `auth.js`, `dashboard.js`, `picks.js`, `picks_firebase.js`.

**Goal**: the existing pages work end to end against the new league-scoped API — signup, league create/join (basic, can be a plain form for now), making picks, dashboard leaderboard, league switcher dropdown.

**Checkpoint**: sign up → create a league → open a second browser profile/incognito, sign up as a different user, join via the 6-digit code → both make picks on `picks.html` → dashboard's league dropdown switches between leagues correctly (if either account is in more than one) → submit locks further edits → leaderboard reflects both players correctly.

**✅ Verified 2026-08-10** via a real headless-browser run (Playwright, two separate browser contexts simulating two users) against real signup/create/join/pick/submit flows — full checkpoint passed. Two real bugs found and fixed along the way, both worth remembering:
- **Signup race**: `signup.html`'s inline "already logged in → redirect" guard used a persistent `onAuthStateChanged` listener, which also fires the instant `auth.js`'s own signup handler creates the account (that's an auth-state change too) — redirecting to `dashboard.html` *before* `updateProfile()`/the profile PATCH finished, so the display name silently never got set. Fixed by unsubscribing after the first invocation, so the guard only checks "was I already logged in when this page loaded," not every subsequent change caused by the page's own actions.
- **`/scores` dropped zero-pick members**: `computeScores()` only produces entries for uids that have at least one picked week, so a brand-new league member with no picks yet was completely invisible on the leaderboard instead of showing up at 0. Fixed by having the route iterate the league's actual member list and default to a zero record for anyone missing from the computed scores — deliberately left `/stats` as-is (only showing players with real picks), since "fun stats" for someone with nothing played isn't meaningful.
- Also found/fixed a `dashboard.js` race: an unconditional `showSection("leaderboard")` call at the bottom of `DOMContentLoaded` could fire before Firebase Auth resolved whether anyone was logged in, throwing "Not signed in" if `localStorage` already had a league ID saved from a previous session. Removed it — the `onAuthStateChanged` listener already triggers the first render itself, in both the logged-in and logged-out branches.

## Phase 5 — New UI surfaces + schedule builder

Covers every feature that has a backend route (Phases 3/3b) but no frontend consumer yet, plus the one existing tool that needed an explicit home:

- ✅ **League management UI**: built as a dedicated `leagues.html` "Your Leagues" screen (real design work from a hand-drawn wireframe, not just plain forms) — league list with an owner-only gear icon opening a management panel (rename, invite code display, member list with kick, transfer-ownership, archive). The header's league-name dropdown (on `dashboard.html`) is a fast shortcut for switching without leaving the page; clicking the "Pick 5" logo returns to the full `leagues.html` screen.
- ✅ **Two-tier profile editing**: global edit-profile lives on `leagues.html` (`users/{uid}` via `/api/profile`); per-league edit-profile lives behind the settings gear inside a league's dashboard (`PATCH /api/leagues/:id/members/me`).
- ✅ **Message board UI**: a 💬 icon in the dashboard header opens a modal with post feed + compose box, delete affordance for owner/author.
- ✅ **"My Week" page**: built as the new "Dashboard" tab (not a separate page — the wireframe put it there) — bonus pick, teams to watch, hate-watch list, and the win-% figure. `winProbability.js`'s Monte Carlo simulation built alongside it. Consumes `GET /api/leagues/:id/my-week?week=N`.
- ✅ **League stats / Hall of Fame page**: built as a 📊 modal in the dashboard header (not a separate page), matching the Message Board/Settings pattern. Two tabs: "This Season" (`GET /api/leagues/:id/stats`) and "Hall of Fame" (year-picker, `GET /api/leagues/:id/seasons/:year`). Header order was reconfigured per explicit user request to (left to right): Hello, [name] → 💬 Message board → 📊 League stats → ⚙ Settings → Log Out. Verified against a fresh test league's empty state and against real Sunroom 2025 historical data (numbers match the Phase 3 curl verification).
- ✅ **Schedule builder**: `src/js/util/fetch_game_data.js` rewritten (2026-08-10) to use ESPN's JSON API instead of HTML-scraping via cheerio — the old scraper never actually produced `times.json`/`dates.json` in the first place, only an unused `games.json`. `npm run build-schedule` now correctly regenerates both files; `cheerio` dropped from `package.json` as an unused dependency. Also **fixed a real, separate bug this surfaced**: `dates.json` was still last year's (2025) dates, copied over verbatim in Phase 0 — since every cutoff date was in the past, the client's `getCurrentWeek()` heuristic concluded the whole season was over and jumped to week 18. This silently affected `picks.html` too (shipped in Phase 4, never caught until now). Regenerated real 2026 dates fixed it.

**Checkpoint**: ✅ full league-management flow works from the UI; ✅ message board works in-browser; ✅ My Week tab renders real data (bonus/teams-to-watch/hate-watch/win%) verified against a real test league; ✅ League Stats modal (This Season + Hall of Fame tabs) verified against both a synthetic empty-state league and real Sunroom 2025 data; ✅ `npm run build-schedule` runs standalone and produces valid `times.json`/`dates.json` for the real 2026 season. Verified via a full Playwright run: signup → leagues.html → create league → manage-league gear panel → enter league → podium leaderboard → My Week tab (before and after making real picks) → message board post/delete → League Stats modal (both tabs) → per-league profile edit → logo-click back to leagues.html. Zero console errors on the final clean pass. **Phase 5 is complete.**

**Post-Phase-5 fix (2026-08-10) — picks invisible until fully submitted**: a member's picks (and anything derived from them) are now hidden from the rest of the league until they've submitted all 18 weeks via `POST /api/leagues/:id/picks/submit`. Added a `submittedSeasonPicks(league)` filter in `leaguePicks.js` and applied it to `/scores`, `/stats`, and `/my-week`'s hate-watch loop — an unsubmitted member now shows the same zero-default row as a brand-new member with no picks (via `scoresWithNames`'s existing fallback), is absent entirely from `/stats`, and their team picks never appear in anyone else's hate-watch list. `/seasons/:year` (Hall of Fame, past finished seasons) was deliberately left untouched — out of scope for this fix. `winProbability.js`'s simulation still reads all members' raw picks internally to compute the caller's win%, since that's an opaque aggregate number, not picks "appearing." Verified end-to-end against the live server with two real throwaway Firebase test accounts (one submitted all 18 weeks, one picked only week 1 and never submitted) — all three visibility assertions passed, test data fully cleaned up afterward.

Reflash Raspberry Pi OS Lite 64-bit onto the SSD (once it arrives) → reinstall `cloudflared` as arm64 `.deb` → recreate the `pickfivepool` tunnel with **two** ingress rules (the site, and SSH behind a Cloudflare Access application with an email-based login policy) → install Docker Engine + compose plugin. ## Phase 8 — Cutover

Deploy the Phase 6 image to the reflashed Pi, point `cloudflared`'s `config.yml` at the container's port, verify `pickfivepool.com` end-to-end from an external network **and** confirm SSH-over-Access works from outside the home network, retire the placeholder `pickfivepool-test.service`, delete `.github/workflows/update-data.yml` and the retired `src/js/util/*` scripts, reboot the Pi to confirm everything survives unattended.

## Pre-launch hardening TODOs (specced, just not built yet)

- **Gate `dashboard.html` on submission status**: a user should only be able to reach a league's `dashboard.html` if they're a member of that league AND have submitted all their picks for it (`POST /api/leagues/:id/picks/submit` completed). Right now nothing stops an unsubmitted member from opening the dashboard directly. Needs a client-side (and ideally server-side, e.g. a lightweight `GET /api/leagues/:id/submission-status` check) redirect back to `picks.html` if not yet submitted. Raised 2026-08-10 alongside the picks-visibility fix below; deliberately deferred since it's a routing/UX change, not a data-leak risk on its own.

## Still genuinely open (not a scope decision — no spec exists yet)

Three items from the original roadmap were flagged with a "?" by the roadmap itself, not just deferred by convenience: **multiple co-owners per league** (single owner + transfer is what's being built instead), **custom per-league scoring rules**, and **per-league pick deadlines / roster size settings**. These aren't scheduled into any phase above because there's no concrete design to build yet, not because they were cut — revisit if/when there's an actual spec for what they'd do.
